# TP 슬롯 예약 — 논문이 정하지 않은 것과 우리의 선택

> 병합 시 `docs/paper_faithful/design_analysis.md` §5 로 접어 넣을 것.
> 별도 파일로 둔 이유는 그 문서를 2×A100 쪽 작업과 동시에 편집하면 충돌하기
> 때문이고, 내용상으로는 §5 항목이다.

## 먼저, 무엇이 논문에서 온 것이 아닌지

이 저장소가 논문에 귀속시키는 TP 관련 기술은 **한 줄뿐**이다
(`design_analysis.md:233`):

> 논문은 한 모델의 TP 샤드들이 같은 GPU 를 공유하지 않도록 제약한다.

그게 전부다. 저장소에 논문 원문(PDF)은 없고, `worker pool` 을 논문 메커니즘으로
귀속시킨 문장도 없다 — 그 단어는 코드 논의에만 등장한다.

**worker pool 은 논문 메커니즘이 아니라 공개 프로토타입의 구현이다.** 논문이
기술하는 것은 빠른 활성화/마이그레이션이고(§6), worker pool 은 프로토타입이
그것을 얻는 방법이다. 측정된 차이가 그 이유를 보여준다:

| | 소요 |
| --- | ---: |
| 엔진 기동 (프로세스 + CUDA 컨텍스트 + 메모리 풀) | **41 s** |
| 이미 뜬 슬롯에 모델 활성화 (Llama-3.2-1B, TP=2) | **0.91 s** |
| 같은 것, Llama-3.1-70B TP=4 | 5.9 ~ 7.0 s |

따라서 **"TP 슬롯을 어떻게 예약하는가" 는 논문이 답할 수 있는 질문이 아니다.**
논문에는 슬롯 풀이라는 대상 자체가 없다. 아래는 전부 구현 선택이며, 충실도
주장이 아니다.

## 선택: 정적 그룹 멤버십

TP=k 그룹은 **서로 다른 k 개 GPU 의 튜플 + 워커 슬롯 id 하나**로 서버 기동
시점에 고정된다. 엔진 하나가 k 개 스케줄러 프로세스로 이를 span 한다. 슬롯은
rank0 의 GPU 가 **소유**하고, 나머지 k-1 개 GPU 에서는 같은 슬롯 id 가
**영구 예약(shadow)** 되어 다른 무엇에도 배정되지 않는다.

**왜 정적인가.** 대안은 활성화 시점에 k 개 풀에서 슬롯을 동시에 잡는 것인데,
그것은 분산 획득이고 부분 실패 시 롤백이 필요하다(핸드오프가 예상한 작업).
정적 멤버십에서는 활성화가 rank0 의 풀 **하나**만 건드리므로 부분 상태가
아예 존재하지 않는다. 롤백할 것이 없다.

**대가 — stranded capacity.** 비-rank0 GPU 의 예약 슬롯은 그 그룹이 유휴여도
TP=1 모델이 쓸 수 없다. 4 GPU / `workers_per_gpu=1` / TP=2 전 쌍 구성에서
GPU 당 슬롯은 다음과 같다:

```
GPU0: [0, 1, 2, 3]   GPU1: [0, 1, 4, 5]
GPU2: [0, 2, 4, 6]   GPU3: [0, 3, 5, 6]
```

슬롯 0 만 TP=1 이고 나머지 3 개는 TP=2 그룹 몫이다. 이 낭비는 실측이 아니라
구조상 그렇다. `--tp-max-groups` 로 후보 그룹 수를 줄이면 낭비도 줄지만
배치 자유도가 함께 줄고, 그러면 anti-affinity 가 구속할 여지도 줄어든다.
드롭된 그룹은 조용히 빠지지 않고 로그에 남는다.

**전 k-부분집합을 후보로 두는 이유.** 그룹이 하나뿐이면 anti-affinity 는
구성상 자동 만족되어 측정할 대상이 없어진다. 4 GPU 에서 TP=2 의 후보를 6 개
전부 열어둔 것은 제약이 구속력을 가질 수 있게 하기 위한 실험 설계이지,
프로덕션 권고가 아니다.

## 선택: 그룹 정보를 공유 자료구조에 넣지 않는다

핸드오프 2단계는 "컨트롤러가 TP 그룹을 멀티-GPU 로 유지" 하라고 적었다. 이를
문자 그대로 — `ModelInstanceState.gpu_ids` 를 그룹 전체로 — 구현하면 컨트롤러가
첫 스케줄링 사이클에서 죽는다. 추측이 아니라 측정된 회귀다(`aa-on` 4/4 → 0/4):

```
simple_global.py:239-240
    for gpu_id in instance.gpu_ids: model_active_instances[gpu_id] = ...
    assert len(model_active_instances) <= 1
```

이 assert 는 "한 모델의 활성 인스턴스는 최대 한 GPU 에만 있다" 를 강제한다.
그 파일은 KV migration 작업 구역이라 건드리지 않았다.

**선택:** 공유 표현은 프로토타입 그대로 두고, 그룹을 `KVPRGlobalPolicyTP` 안에서
추적한다. 설정된 배치에서 seed 하고 이 정책이 이동을 낼 때만 갱신한다. 추적값과
런타임이 보고하는 rank0 GPU 가 어긋나면 런타임을 신뢰하고 슬롯 플랜에서 그룹을
다시 유도한다 — 우리 기억이 아니라 런타임이 권위다.

`controller_global.py:97-99` 의 rank0 축약 제거는 그대로 유지했다. 그것은
컨트롤러가 고려하는 GPU 집합에 대한 것이고 인스턴스 표현과 무관하며, 전 모델이
tp_size=1 이면 예전 줄과 동일하다.

## 확인이 필요한 것 (논문 원문 없이는 닫히지 않음)

논문을 직접 읽지 못했고 저장소의 특성화에 의존했다. 원문이 확보되면 확인할
가치가 있는 지점:

* 논문이 TP 모델의 **수용/배치**를 슬롯이나 풀 같은 추상 위에서 기술하는가.
  기술한다면 위 정적 예약 설계는 재검토 대상이다.
* anti-affinity 가 **배치 시점의 제약**인지, **런타임 불변식**인지. 여기서는
  Algorithm 1 의 argmin 후보 필터로 구현했다(배치 시점). 런타임 불변식이라면
  위반 배치를 거부하는 검사가 따로 필요하다.
* 논문이 TP 그룹의 **마이그레이션**을 다루는가. 여기서는 관측만 했고
  (그룹 [0,1] → [0,2]) 설계 목표로 삼지 않았다.
